## Findings and designs

### 1. Test fixtures are environment-dependent (High)
**Problem.** `createTestRepo()` in `test/git-utils.test.ts` and `test/integration.test.ts` runs
plain `git init`, then tests assert against a branch literally named `main`. On hosts where
`init.defaultBranch` is unset (git defaults to `master`, as on this host), 5 tests fail —
3 in `git-utils.test.ts`, 2 in `integration.test.ts`. Evidence: `git checkout main` →
`pathspec 'main' did not match`; `git worktree add <path> main` in the bare-repo test exits 128.
**Design.** Make the fixture deterministic: `git init -b main` in both fixtures. No product
change; the tests' intent is clearly `main`.
**Also.** `test/utils.test.js` and `test/integration.test.js` are stale transpiled duplicates of
the `.ts` versions and are never executed (`vitest.config.ts` includes only `test/**/*.test.ts`).
Deleted.

### 2. `wt new` / `wt setup` report success they did not achieve (High)
**Problem.** When the resolved target directory already exists but is not a worktree of the
requested branch, both commands print a warning and then fall through to the success path:
they open the editor on the unrelated directory and print `Worktree created/opened at …`.
`wt new other-branch --path <existing worktree of a different branch>` likewise "reuses" the
wrong worktree silently. `wt pr` already handles both cases correctly with hard errors.
**Design.** Match `wt pr`: resolve the directory against `git worktree list` (via
`findWorktreeByPath`, which normalizes symlinks), then:
- registered worktree on the requested branch → reuse (existing message kept; pinned by test),
- registered worktree on another branch → error naming the actual branch + suggest `--path`,
- anything else → error: not a worktree of this repository + suggest `--path`.
Error instead of adopting/deleting user directories — the safe default.

### 3. Compiled output is tracked and can shadow `src/` in tests (High)
**Problem.** `build/` is committed even though `.gitignore` intends to ignore it: line 40 is
`build/ # Ignore the build output directory`, and gitignore has no trailing-comment syntax —
the pattern matches nothing. Integration/config tests exec `build/index.js`, so a dev who edits
`src/` and runs `pnpm test` without rebuilding silently tests stale compiled code.
**Design.** Fix the ignore rule (`build/` on its own line), `git rm -r --cached build` (files
stay on disk), and make `pnpm test` build first (`pnpm run build && vitest run`). CI already
builds before publishing; README only documents registry installs, so no git-install path
depends on tracked artifacts. Accepting the tradeoff that `npm i -g <git-url>` would no longer
ship prebuilt output (was never a documented install path).

### 4. Stash recovery hash can be lost (High)
**Problem.** `stashChanges` (`src/utils/git.ts`) snapshots dirty state as a **dangling** commit
(`git stash create` + `reset --hard` + `clean -fd`) — it is not in `refs/stash`. The only link
back to the user's uncommitted work is the returned hash, and two code paths could drop it:
1. `applyAndDropStash` logged the git error on failure but never printed the hash.
2. Error exits after stashing called `process.exit(1)` — including from `catch` blocks whose
   `finally` was supposed to restore — which terminates the process before the restore runs.
   All four stashing handlers (`new`, `setup`, `extract`, `pr`) had such paths.
**Landed now.** On restore failure, print the hash and the exact recovery command. Post-stash
error exits now set `process.exitCode` and return, so the `finally` restore always runs
(smoked end-to-end: stashed file restored after the new error path).
**Follow-up design (not landed).** Persist the hash to `<git-common-dir>/wt-stash.json` before
the destructive reset and delete it after a successful restore; on startup, offer recovery if
the file exists. That covers SIGKILL/power loss, which signal handlers and `finally` cannot.
Tradeoff: small on-disk state to reconcile with concurrent `wt` runs.

### 5. `wt --version` is hardcoded (Medium)
**Problem.** `src/index.ts` passes `version("1.0.0")` to commander while releases are 2.x and
versioned by semantic-release (which rewrites `package.json` at publish). `wt --version` has
been wrong since 1.0.0.
**Design.** Reuse the `package.json` load already in `src/config.ts` (`getPackageVersion()`)
and pass that to `.version()`. Locally this reads `0.0.0-development`; published installs read
the released version.

### 6. `wt pr` API fallback assumes the remote is named `origin` (Medium)
**Problem.** `getRepoInfo()` in `src/commands/pr.ts` runs `git config --get remote.origin.url`
while every other code path resolves the remote via `getUpstreamRemote()` (handles
`upstream`/custom names and tracking info). Repos without an `origin` remote fail the REST
fallback even though the CLI knows the correct remote.
**Design.** `getRepoInfo()` resolves the remote with `getUpstreamRemote()` and reads
`git remote get-url <remote>`. Parsing unchanged.

### 7. Shutdown manager hijacks `SIGINT` (Medium)
**Problem.** `src/utils/shutdown.ts` calls `process.removeAllListeners('SIGINT')` on
construction ("prevent duplicate handling") and stores the displaced handler without ever
restoring it. This can break any library that registered `SIGINT` before the first
`onShutdown()` call (prompts/readline-style stdin handling, test harnesses).
**Design.** Register our handler alongside existing listeners; the singleton already
guarantees single registration. Drop the unused `originalSigintHandler` field. Exit semantics
(130 after cleanup, force-exit on second signal) unchanged.

### 8. Dead weight (Medium)
**Problem.**
- `src/utils/workflow.ts` (258 LOC) — `executeWorkflow` and helpers have **zero** importers.
  Its purpose (standardized dirty-check/stash/editor flow) is instead copy-pasted into
  `new.ts`, `setup.ts`, `extract.ts`, `pr.ts` (~60 lines each).
- Deprecated, zero-caller exports: `runSetupScripts` (superseded by `runSetupScriptsSecure`),
  `popStash` (superseded by `applyAndDropStash`), `withCleanup`.
- Test-only seams: `getCurrentBranch`, `getShortBranchName` (production never calls them; only
  tests do).
- `getUpstreamRemote` has an unreachable `master` fallback: the inner call uses
  `reject: false`, so execa never throws into the `catch` that contains it.
- Unused imports in command handlers (`resolve`, `getWorktrees`, …).
**Design (landed).** Delete `workflow.ts` and the dead exports plus their orphaned tests; make
the `master` fallback reachable by iterating `["main", "master"]` (restores documented intent);
drop unused imports.
**Follow-up design (not landed).** The four command handlers should share one small helper for
the dirty-check/stash/SIGINT-restore block (the thing `executeWorkflow` tried to be), e.g.
`prepareWorktree(): { restore }` in `src/utils/workflow.ts` shape — but composition beats the
previous wrapper: commands keep their own `process.exit`/message semantics and call the helper.
Do this as a dedicated refactor with the integration suite green before/after.

### 9. CI publishes without running tests (Medium)
**Problem.** `.github/workflows/publish.yml` builds and runs `semantic-release` with the test
step commented out ("Optional: Add a test step here if you have tests"). Broken code can reach
npm.
**Design.** Add a `Test` step (`pnpm exec vitest run`) after `Build`, before release. The suite
runs against the freshly built CLI (tests exec `build/index.js`).

### 10. `WT_EDITOR` is assumed by tests but unread by the CLI (Low)
**Problem.** `test/integration.test.ts` sets `WT_EDITOR: 'none'` "to disable editor opening in
tests", but no production code reads it. Safety currently rests on every call site passing
`--editor none`; one omission would spawn a real editor during tests.
**Design.** `getDefaultEditor()` returns `process.env.WT_EDITOR` when set (env overrides
config — standard CLI convention), making the existing test intent real. `shouldSkipEditor`
already treats `none` as skip.

### 11. Branch-name validation misses git ref rules (Low)
**Problem.** `validateBranchName` (`src/utils/paths.ts`) catches spaces/`~^:?*[\]`, `..`,
`.lock`, but git (`git check-ref-format`) also rejects `@{`, a leading `-`, leading/trailing
`/`, `//`, trailing `.`, and `.`/`@` components. Invalid names currently fail deep inside
`git worktree add` with a confusing error and a rolled-back atomic op.
**Design.** Add the missing checks; each mirrors a rule git enforces, so no valid branch is
rejected. Extend the existing `validateBranchName` test table.

### 12. Docs drift (Low)
- `TESTING.md` "Merge" section says the source worktree is removed after `wt merge`; the
  command preserves it unless `--remove` (README is correct). Its purge instructions describe
  a per-item `y`-prompt; the actual UI is a multiselect + confirm.
- `.cursor/rules/project.mdc` claims `files: ["dist"]`; the package ships `["build"]`.
**Design.** Correct both. `CHANGELOG.md` is generated by semantic-release — left alone.

### 13. Dual lockfiles (Info — not landed)
Both `package-lock.json` and `pnpm-lock.yaml` are committed; `packageManager` and CI use
pnpm 9.5. Per task constraints the npm lockfile is kept. Risk: the two can drift silently.
Recommendation: pick one in a dedicated decision (pnpm is already the declared manager);
until then CI pins `pnpm install --frozen-lockfile`, which only enforces `pnpm-lock.yaml`.

## Product decisions made (documented per instructions)

1. Existing non-worktree directory at the target path → **hard error**, never adopt or delete
   (Finding 2).
2. Existing worktree on a different branch than requested → **hard error** naming the branch,
   consistent with `wt pr` (Finding 2).
3. `WT_EDITOR` env var overrides the configured default editor (Finding 10).
4. CI: tests gate the release; a red suite blocks publish (Finding 9).
5. `wt --version` reports `package.json`'s version (Finding 5).
6. `build/` untracked; git-based installs are not a supported path per README (Finding 3).

## Test policy (what proof changed)

- **Removed** (with their functions, as one batch): `getCurrentBranch` and `getShortBranchName`
  tests — no production caller, i.e. test-only seams; `test/*.test.js` copies — never executed.
- **Kept**: `stashChanges`/`applyAndDropStash` round-trip (real dirty-state contract at the git
  boundary), `validateBranchName` table (user-facing contract), atomic rollback order,
  integration CLI flows.
- **Added** (one owner each, CLI boundary): existing-directory false-success regression,
  branch-mismatch regression, `--version`/package.json consistency; `validateBranchName` table
  rows for the new rules.
- Fixtures: made deterministic (`git init -b main`) instead of asserting whatever the host's
  default branch is.

## Verification

The host was under heavy load during the audit; all checks were run as single targeted
commands (`nice -n 19`), one test file at a time, no parallel workers.

- **Failing-before proof**: the 4 new regression tests were first run against the
  pre-change `build/` output and failed for their intended reasons (false success with
  exit 0 on both directory cases, `--version` reporting `1.0.0`, editor not suppressed
  by `WT_EDITOR`), while the fixture-dependent tests passed with only the
  `git init -b main` change — isolating each fix's effect. After the fixes: all pass.
- `tsc`: clean.
- `test/integration.test.ts`: 16/16 — includes both false-success regressions,
  `--version`↔package.json consistency, `WT_EDITOR` suppression.
- `test/utils.test.ts`: 13/13 — `validateBranchName` table including the new ref rules.
- `test/git-utils.test.ts`: 13/13 — fixture determinism, stash round-trip.
- `test/config.test.ts`: 25/25 — `getDefaultEditor` (now `WT_EDITOR`-aware) via the CLI.
- `test/tui.test.ts`: 25/25 — unchanged code. Total: 92 tests green.
- **Smoke — `wt pr` remote fallback**: throwaway repo whose only remote is named
  `upstream`, `gh` hidden from `PATH`: the REST fallback resolved `octocat/hello-world`
  from the upstream remote and reached the GitHub API (401 with a dummy token). Before
  the fix this failed on `remote.origin.url`.
- **Smoke — stash restore on error path** (PTY via `script`, answering the stash prompt):
  an uncommitted file was stashed, the new existing-directory error triggered, and the
  `finally` restore returned the file (`RESTORED: uncommitted`).
- **Not machine-verified**: the SIGINT change (no signal-injection harness here). It is
  strictly the removal of `process.removeAllListeners('SIGINT')`; suite stays green.

Proof/cost: production −393 net LOC (mostly `workflow.ts` and dead exports), tests −330
net LOC (stale duplicates and orphaned seam proof), +4 focused CLI-boundary regressions.
